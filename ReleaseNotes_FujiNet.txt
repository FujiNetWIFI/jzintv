Release notes for the FujiNet fork.
Based on upstream jzIntv 20200712 (SVN r2110).  See ReleaseNotes_20200712.txt
and earlier ReleaseNotes_*.txt files for the upstream emulator's history.

-------------------------------------------------
 ROM pushes wedging partway through ("BOOTING"):
-------------------------------------------------

A pushed cart could stop dead partway through the transfer, leaving the
console on the config ROM's "BOOTING / DO NOT POWER OFF" screen with the
progress bar frozen (95% for Deep Pockets, other titles elsewhere) and the
title line drawn as garbage.  Deterministic per title: Deep Pockets, Body
Slam, Spiker, Stadium Mud Buggies, Super Pro Decathlon, Super Pro Football
and Pole Position hung, while Chip Shot, Slam Dunk, Commando, Diner and
Hover Force pushed fine.  Each affected ROM loaded and played correctly
when passed to jzIntv directly as bin+cfg, so neither the images nor their
mappings were at fault.

*   src/fujinet/fujinet.h: the raw receive buffer was sized
    FUJI_MB_RX_MAX + 128 = 640 bytes.  That constant bounds the *mailbox's*
    reply window in cartridge RAM, an address-space budget -- but the same
    buffer also has to hold whole SLIP-encoded frames off the wire, and the
    ROM push's NETCMD_WRITE frames carry DISK_SECTORBUF_SIZE (512) bytes of
    payload.  Decoded that is a 6-byte header + 512 = 518; SLIP escaping of
    0xC0/0xDB can nearly double it, 1038 worst case.  A chunk of graphics
    data with a long run of 0xC0 -- an ordinary two-pixel column pattern --
    overflows 640 comfortably.  Now sized from FUJIBUS_RAW_RX_MAX (1088),
    backported from the RP2040 firmware's fuji_mailbox.h along with its
    rationale and the FUJI_BOOT_ERR_TOOBIG / _BANKSW codes.
*   src/fujinet/fujinet.c: that overflow was unrecoverable, which is what
    turned it into a hang rather than a failed boot.  The RP2040 reference
    keeps its rxlen/seen_end as locals inside one deadline loop, so an
    over-long frame simply times the transaction out and the next one
    starts clean.  Here they live in fujinet_t and persist across ticks
    (a frame can straddle any number of them), and nothing reset them on
    the failure paths -- so once rxlen reached sizeof(rxbuf) without two
    frame delimiters, the accumulate loop's own guard was false on every
    subsequent tick: not one more byte drained, no frame parsed, no DBC ACK
    sent, ever.  New fujinet_rx_resync() on both the buffer-full and
    parse-failure paths.  Back-to-back frame delimiters are also collapsed
    now, the way SLIP treats empty frames.
*   src/fujinet/fujinet.c: fujinet_rom_buf_append() assigned realloc()'s
    result straight back over the only pointer to the in-flight image, so a
    failed grow leaked it and then memcpy'd into NULL.  It now keeps the
    existing buffer and fails the boot with FUJI_BOOT_ERR_TRUNCATED.

---------------------------------
 Booting the larger cartridges:
---------------------------------

The 32K and 48K titles (Diner, Hover Force, and the rest of the INTV-era
sports/action carts) failed to boot from a FujiNet push.  Fixed by bringing
the boot receiver in line with the RP2040 firmware, plus one problem that
only exists in the emulator:

*   .cfg mappings are now clamped at end-of-file, matching SDK-1600
    bin2rom.  The published .cfg collections describe each title's largest
    layout and rely on ranges past EOF simply falling away; the old parser
    dropped any such line whole, so a 32K cart lost its $9000 segment
    entirely.
*   A mapping that covers the FujiNet mailbox window ($9C00-$9F3F) no
    longer rejects the boot.  The game starts with the mailbox disabled for
    the session -- reads return the bus AND-identity so the game's own ROM
    reads through, writes drop -- restored only by a session restart.  This
    is the policy the RP2040 firmware now applies.  Nearly every 32K/48K
    cart maps 12K at $9000 and so lands in this case.
*   [memattr] cartridge RAM declarations are parsed (8- or 16-bit, nothing
    below $4000, total capped at the hardware's 0x2800-word budget).
*   The size-guess table (used when no .cfg arrives) gained the 40KB
    (8K@$5000 + 12K@$D000) and 48KB (8K/12K/4K INTV) shapes.
*   An abort-CLOSE (0x01 payload) from the FujiNet side now discards a
    failed push instead of booting partial data, and the .cfg is consumed
    per push so a stale sidecar can't leak onto the next mount.
*   periph/periph.c, icart/icart.c: new periph_unregister() /
    icart_unregister().  periph_register() only ever adds to the bus
    address decode, which is all a machine built once at startup needs --
    but the FujiNet hot-swap re-registers the same icart_t over a new
    memory map, and the outgoing cart's ranges stayed bound forever.  On
    the Intellivision's wire-AND bus the CPU then saw the AND of old and
    new: the config ROM's 8-bit RAM window at $8000-$9BFF silently masked
    the high byte off every pushed game with a segment there.

---------------
 New features:
---------------

*   FujiNet mailbox peripheral (src/fujinet/)
    *   Emulates the RP2040 side of the FujiNet-for-Intellivision bridge
        (see fujinet-firmware/pico/intellivision/).  On real hardware, an
        RP2040 cart exposes a "mailbox" register window in Intellivision
        RAM and relays each transaction to a FujiNet (ESP32-S3) over USB
        CDC as a SLIP-framed FujiBus packet.  jzIntv instead speaks the
        same FujiBus frames over a TCP socket, using fujinet-firmware's
        "Bus Over IP" (BoIP) feature -- a transparent byte stream with no
        framing of its own, so the bytes on the wire are identical to
        what the RP2040 would send over USB.  fujinet-firmware is the TCP
        server; jzIntv is the client.
    *   New command-line options:
        *   --fujinet[=host[:port]]
            Enable the FujiNet mailbox peripheral at $9C00-$9FFF,
            connecting over BoIP to a fujinet-firmware instance.
            Defaults to localhost:1985.  If no ROM is given on the
            command line, boots the built-in FujiNet config ROM (WiFi
            setup / host slots / directory browser) instead of looking
            for game.rom; an explicit ROM argument always overrides
            this.
        *   --fujinet-debug
            Trace FujiNet mailbox transactions and FujiBus frames to
            stdout.
        *   --fujinet-bootdump=PREFIX
            The emulator can't reload the cart the way real RP2040
            firmware does, so it can't complete a MOUNT_IMAGE boot --
            but it can still receive the same DBC-addressed ROM/.cfg
            push a real board would.  With this set, jzIntv writes what
            it received to PREFIX.rom and, if a .cfg sibling was
            pushed, PREFIX.cfg.
    *   Embedded FujiNet config ROM (src/fujinet/fujinet_config_rom.c/h),
        generated from the fujinet-config repo's intv/config.rom via
        src/fujinet/mkconfigrom.py, so `--fujinet` works out of the box
        with no external ROM file.
    *   DBC (FUJI_DEVICEID_DBC) inbound-frame handling: when
        fujinet-firmware pushes a ROM (and optional .cfg sibling)
        mid-transaction -- the same push a real board receives --
        jzIntv decodes it into the running icart_t and resets the
        console, effectively hot-swapping the loaded cart.
    *   New example: examples/fujinet/ (fujitest.bas / fujitest.rom),
        a minimal FujiNet mailbox test program.

----------
 Changes:
----------

*   cfg/cfg.c, cfg/cfg.h, cfg/mapping.c, cfg/usage.c
    *   Wired up FujiNet option parsing, peripheral registration at
        $9C00-$9FFF, and boot-from-config-ROM handling.
    *   Note: the FujiNet mailbox window overlaps the tail of the JLP RAM
        window, so --jlp and --fujinet should not be combined in the same
        session.
*   icart/icart.c, icart/icart.h
    *   Support for loading a cart from an in-memory buffer, used both by
        the embedded config ROM and by DBC-pushed cart reloads.
*   plat/plat_lib.c, jzintv.c, jzintv_em.c
    *   Plumbing to let the FujiNet peripheral drive a cart reload and
        console reset from within the emulator's main loop.
*   Makefile.common, Makefile.emscripten_sdl1, Makefile.emscripten_sdl2
    *   Build the new fujinet/ object files.

-------------------------
 New files:
-------------------------

*   src/fujinet/fujinet.c, fujinet.h
        The mailbox peripheral itself: connection/transaction state
        machine, register window, DBC push handling, cart-reload glue.
*   src/fujinet/fujibus.c, fujibus.h
        FujiBus SLIP framing (encode/decode).
*   src/fujinet/fn_sock.c, fn_sock.h
        Minimal non-blocking TCP socket wrapper (POSIX + Windows).
*   src/fujinet/fuji_mailbox.h
        Mailbox register layout; mirrors the fujinet-firmware RP2040
        firmware's copy verbatim -- keep in sync by hand if it changes
        upstream.
*   src/fujinet/fujinet_config_rom.c, fujinet_config_rom.h
        Generated embedded config ROM image and length.
*   src/fujinet/mkconfigrom.py
        Regenerates fujinet_config_rom.{c,h} from a built config.rom.
*   src/fujinet/subMakefile
        Build rules for the above, plus the `fujinet-config-rom` phony
        target for regenerating the embedded ROM by hand.
